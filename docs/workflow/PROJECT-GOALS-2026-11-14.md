HOI4 Companion should help a player decide what to do, understand why, build an editable campaign strategy, and carry that strategy into military and economic preparation. It should use the installed game's sources, retain the player's work, and distinguish reliable facts from assumptions. Trustworthy observations and authorized gameplay assistance extend that product later.

The foundation is substantial: a Windows application, offline reference index, manual campaigns, focus planning, history, source explanations, optional AI strategy generation, military resource models, and a shared observation platform. The principal delivery gap is a useful, coherent player journey through those capabilities. Backend delivery has outpaced usability and qualification.

There is no defensible single completion percentage for the full project: the roadmap combines a bounded companion with long-term autonomous gameplay, and the final supported configuration/content denominator has not been approved. The estimates below assess each product outcome, including validation and usability work. They are engineering judgments, not measured semantic coverage or forecasts.

## Technical summary

The application uses a sandboxed Electron/React renderer, one existing Node service, ordered script parsing, a persistent reference index and SQLite campaign data. Planning uses versioned profiles, `CampaignPlan`, expected profile/index revisions and reviewed preview/apply fingerprints. Source mechanics flow through the deterministic interpreter and the planning coverage gate. AI prose cannot raise confidence or certify engine behavior. Bridge SQLite, the shared gateway/receipts and authenticated MCP adapters remain separate from source analysis and manual planning assertions.

The source-grounding problem has two layers. Identifiers and source hashes can be valid while an outcome is still unsupported. The retained successful provider proposal had 17 valid unique typed references but 106 blocking interpretation/campaign checks. Additional prose or successful HTTP calls cannot close those checks. The full-release census is a conservative obligation tracker, not a quality percentage or a count of distinct mechanics.

The current installed-source audit identifies 1.19.5.0 while retained semantic qualification targets 1.19.4.2. Thirty-eight of 39 pinned files matched and launcher settings changed; that demonstrates byte equality only. Active DLC/tree applicability and engine behavior still need evidence. Legacy Germany/Hungary and no-NSB fixtures cannot certify an all-DLC campaign. Combat currently qualifies zero of the five numerical division metrics: totals and deltas remain null/unsupported.

Draft safety also has distinct layers. The older planner/campaign registry protects its own objects; NAV-01 added Division Lab drafts. The audited AI/manual whole-strategy editor retained its objective and proposal in component state, so unmounting could erase them without an unsaved warning. STRATEGY-DRAFT-01 extends the existing protection to that editor. Its explicit policy is in-window retention with save/download before reload or restart; this is not crash-durable autosave.

## Execution gameplan

1. **Finish the closest goal now: protect whole-strategy work.** Builder implements campaign-keyed retention and destructive-action confirmation, pending-write accounting, global review/download/discard and late-response safety. Independent reviewer checks exact source. Run focused unit, browser and extracted Windows lifecycle checks. Deliver to main after hosted CI. Exit: the original data-loss reproduction and its failure/race variants pass; saved strategies reopen after full process restart. See [STRATEGY-DRAFT-01](../application/STRATEGY-DRAFT-01.md).
2. **Pin the qualification target.** Produce a short supported-configuration record and current-patch/applicability fixtures. Exit: affected code accepts matched inputs and refuses mismatches without relabeling historical evidence. This precedes new confidence claims and qualified military totals.
3. **Ship one player journey.** Implement Campaign-first B with real services and source-bounded Germany context. Keep the existing tools accessible. Exit: a player enters a Germany military objective, answers missing-state questions, edits a provisional strategy, uses a military comparison, saves, navigates and reopens without loss; owner judges it useful. Follow with directly comparable campaign ideas (style/fun, difficulty rationale, preparation, DLC and risks) and useful stale-guide recovery rather than a blocked dead end; label editorial judgments separately from calculations.
4. **Close the mechanics critical to that journey.** Separate event/path work from military aggregation work so each has a reviewable semantic contract. Exit: selected positive, refusal, alternative and changed-source cases have independently supported outcomes; unresolved areas remain visible. Portugal remains a second representative journey.
5. **Finish observation usefulness before control.** Complete the separate read-only Q&A pilot, current session identity and selected field qualification. Exit: sustained capture and paired questions agree with independent displays and disclose every gap. PR #4 stays separate until its own criteria pass.
6. **Run the finite release acceptance.** Check current package, lifecycle/faults, migration, accessibility, performance, physical offline behavior and approved content coverage once against frozen inputs. Close or explicitly disposition every relevant ledger item. Exit: actual owner acceptance and the existing release gate pass; a development source push does not imply this exit.
7. **Qualify assistance incrementally.** First one ordinary focus action, then research, then approved batches. Exit for each action: intended effect independently observed, duplicate/uncertain requests safe, stop/cancellation demonstrated. Do not put autonomous gameplay on the initial companion release's critical path.

Work can proceed in parallel only across agreed interfaces: Campaign-first UI, bounded source semantics and military equations. Share one baseline and service; merge small independently reviewed changes. Do not repeat broad historical suites when inputs are unchanged and focused evidence answers the question. Rebuild/retest the affected runtime when code changes, and keep failed evidence alongside the diagnosis.
